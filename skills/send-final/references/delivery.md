# Deliveries

Revision: 9

Read [Project](project.md), [Orders](orders.md), [Versions](versions.md), [Intentional selection](sending.md), and [Format](format.md). Both send modes follow this protocol; `send-final` adds reassessment, decisions and closure. Never claim success from an agent message or saved phase alone.

**Before selecting an order or payload**, follow [Send recovery](send-recovery.md). A packaged retry branches directly to remote reconciliation and completion using its saved order, activation token, kind, tag and exact ZIP. A published final may need completion even though its issue is already closed or another assignment is now active. Run the fresh-send steps below only after pending operations have been reconciled.

## Select and capture

For a new/unpublished operation, execute [Observed cancellation](cancellation.md) after complete bound issue/release discovery and **before capture**. Resume its saved apply/disclosure records first. If it observes a request or hand closure for the intended order, finish/report cancellation and stop this send, preserving every pending record, snapshot, ZIP, draft, checklist, tag reservation and design folder. Run the same owner immediately before publication with fresh complete observations. An earlier successful check never authorizes a later unchecked publication. A packaged matching published final follows Send recovery first and is never cancelled by a later request.

1. Reconcile `.designeritl/pending/` and `state.pendingDeliveryIndex` before a new send. A valid existing capture/ZIP is authoritative; do not recapture source edits. Multiple pending deliveries require an explicit choice. Preserve unsupported or conflicting evidence and stop.
2. Use Sending's `selectOrder` with complete current issue/release observations. Reuse the active available open order or obtain an explicit open-order choice before asking what to send. An unstarted choice uses Orders' canonical activation/checklist policy. Preserve repository/order and activation UUID for compare-and-clear. Apply observed cancellation before capture. A closed order without matching published final is cancelled. A published final blocks a new delivery.
3. Use [Intentional selection](sending.md) to select the files, folders or numbered version and reserve a UUID/tag. For a file delivery, tell the designer that the developer needs the updated Inbox to receive this format.
4. Read the saved record under `.designeritl/pending/UUID/record.json` and create its snapshot parent. For a file delivery (`payloadType: files`), call Format's `captureFiles(record.sourceFiles, record.stagingPath, record.selectedInventory)`. For a numbered version, call `capturePrototype(record.sourcePath, record.stagingPath)`. Both compare source-before, copied and source-after inventories and preserve empty directories. Save `capturedInventory`, `payloadSha256` and `capturedDirectories` only after a coherent capture, through Project's validated owner-record replacement. Reconcile partial staging through Send recovery. All later checks use the saved capture.

## Assess the captured design

5. For a numbered version, establish [Versions portability](versions.md) against the capture. Open its entry HTML directly, exercise relevant states and interactions, and observe network attempts. Save evidence with the payload hash and performed or omitted checks. Unresolved dependencies, missing required checks or format violations block publication. For a file delivery, proceed to packaging after coherent capture and leave the selected files as supplied.
6. For final delivery only, use Orders' `createOrders(format).readChecklist(projectRoot, orderNumber)` to validate the saved agreement and checkpoint, and retain its scope, local checkedOrdinals and taskContext as separate snapshots. `scopeSha256` is `scope.originalBodySha256`, never a hash of tick-edited Markdown or the current remote issue. Assess **every** `scope.tasks` definition in its original order against the captured selected version as fulfilled, unfinished or unknown, with actual evidence or a reason for uncertainty. An older delivery selection may contradict current local ticks; assess its snapshot, not `.current`. Unknown counts as unfinished. Freeze `evidence/reassessment.json` as exact UTF-8 JSON containing payloadSha256, scopeSha256, `agreedScope: scope` and ordered `{ordinal,result,evidenceOrReason}` tasks. The embedded original body proves the complete agreed task universe to reception. Delivered unchecked ordinals are every task not both locally checked and reassessed fulfilled. Preserve local progress; sending or acknowledging does not tick tasks.
7. For final delivery only, disclose the exact unchecked task numbers/text and reassessment reasons. Obtain the designer's applicable completion choice. An explicit final-delivery invocation authorizes a fully fulfilled, locally checked scope; a sufficiently specific conditional authorization may cover its stated conditions. Unfinished, unknown or locally unchecked tasks require the designer's explicit acknowledgment of every derived ordinal. Decline or missing authorization retains evidence and leaves the order open before packaging. Freeze `evidence/decision.json` as exact UTF-8 JSON with `schemaVersion:2`, payloadSha256, scopeSha256, reassessmentSha256, acknowledgedUnfinishedOrdinals, the genuine explicitDesignerStatement and UTC recordedAt. Hash stored exact bytes. Any changed payload, agreement, reassessment bytes or applicable task progress invalidates the earlier decision. Preserve stale evidence and obtain a new applicable choice. A user who wants a different version can explicitly replace the un-packaged capture through Send recovery, then repeat portability, reassessment and completion.

## Freeze and publish

8. Write one exact `manifest.json` in pending storage using Format. For a nonfinal send, use Sending's `nonfinalManifest` as specified in Intentional selection. A file delivery uses the note saved at reservation. For a numbered version, write a `deliveryNote` with a summary naming the order and version, `outsideOrder` and `workInProgress` (explicit `None` when applicable). Include the complete captured inventory and directories. Retain scope hash and local progress separately from final reassessment and decision evidence. Call `packageDelivery` on stored manifest bytes and the snapshot. Persist `delivery.zip`, `descriptor.json` and human release notes containing its single `designeritl-delivery` block. Read back and call `verifyDelivery` before proceeding. Persist payload, ZIP and manifest hashes and asset size in the record, then call `verifyPendingDelivery(pendingRoot, repositoryId)` before remote mutation. Reuse the completed package on retry.
9. Follow [Send recovery's draft creation guard](send-recovery.md#guard-draft-creation) with complete REST and GraphQL release pages and tags. A zero-match listing alone never permits creation. Format's `beginDraftCreation` must durably save and reread a descriptor-bound attempt before the single `gh api --method POST repos/OWNER/NAME/releases --input REQUEST_JSON` with the saved tag/body and `draft:true`. Save its raw successful JSON at the attempt-specific evidence path and call `recordDraftCreateReceipt` as specified by the guard. After any response, reconcile the same identity. An unresolved attempt without a receipt or a legacy record remains read-only until its release appears. A receipt-backed exact direct read can return `resume-unlisted` for asset work while publication waits for a listing. Independently proven non-dispatch follows the retained-proof branch. Draft creation is not publication.
10. For a matching owned draft, list all assets by release ID and upload/download by release/asset ID using the exact commands in Send recovery. This also supports `resume-unlisted`. Download to separate verification staging and verify exact bytes with the descriptor. Reuse exact owned assets. Preserve evidence of a bad owned unpublished asset and require a deliberate repair before deleting only that asset. Never blind `--clobber`, alter a foreign asset or mutate a published release.
11. Reverify saved capture, manifest, evidence bindings and ZIP. Refresh complete release listings and call `requireDraftPublication(record, descriptor, pages, complete, tags, releaseId, observations)` from Format. Only a unique listed matching draft can pass; a receipt-backed direct read permits asset work only. Re-read complete cancellation/issue state immediately before publication; observed cancellation refuses publication and leaves the draft/evidence intact. If all gates pass, publish that exact release ID with `gh api --method PATCH repos/OWNER/NAME/releases/RELEASE_ID -F draft=false`. A lost response is reconciled by reading the release, never by recreating it.
12. Fetch actual release metadata (tag, draft=false, ID, single descriptor and asset identity). Download its actual asset to fresh verification staging and `verifyDelivery` again. Compare all saved identity fields and exact ZIP/manifest hashes. Unknown remote state or a mismatch prevents closure or a success claim.

## Complete

13. A nonfinal verified publication leaves the issue open, retains assignment and working marker, and records completion. Before any final order closure, refresh complete issue observations, parse them with `observedOrderIssues` and require `orderIssueProblem(rows,N)` to return null and the target to be a supported work order. A malformed issue or relation stops closure for that order only: report its number/reason, preserve the published artifact and pending evidence, and never modify the malformed issue. A final verified publication otherwise closes the order: `gh issue close N --repo OWNER/NAME --reason completed`; then independently read back closed status. If publication succeeded and closure failed, retry closure/bookkeeping only, reusing frozen evidence and exact ZIP. An already closed issue following matching published final completes bookkeeping. Developer acceptance is separate and never recorded as implied approval.
14. Re-read current state and clear assignment only for final completion, and only if repository/order AND activation UUID equal `record.assignmentToken`. Preserve a later activation, even of this same order. Preserve checklists and working marker. Through Project's complete-record replacement, add or reconcile one `completedDeliveries` entry containing delivery/repository/order identity, tag/kind, release/asset IDs, exact hashes, evidence path and verification/completion time; remove only this UUID from `pendingDeliveryIndex`. Re-read state and verify these effects before marking the pending record locally complete. An existing completion entry must match the same identity/hashes; conflicting entries stop bookkeeping. Retain capture/ZIP and observations after success; cleanup is a later explicit action. Report exact tag/UUID, verification and any remaining closure failure.

Incoming requests created after the final pre-publication check do not withdraw a published delivery. Inbox later names such deliveries while applying cancellation; a request after published final has no effect. This follows observed cancellation, not an impossible atomic GitHub issue/release transaction.
