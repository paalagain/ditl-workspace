# Deliveries

Revision: 6

Read [Project](project.md), [Orders](orders.md), [Versions](versions.md), [Intentional selection](sending.md), and [Format](format.md). Both send modes follow this protocol; `send-final` adds reassessment, decisions and closure. Never claim success from an agent message or saved phase alone.

**Before selecting an order or version**, follow [Send recovery](send-recovery.md). A packaged retry branches directly to remote reconciliation and completion using its saved order, activation token, kind, tag and exact ZIP. It does not run fresh selection, recapture or acknowledgment, and a published final may need completion even though its issue is already closed or another assignment is now active. Run the fresh-send steps below only after pending operations have been reconciled.

## Select and capture

For a new/unpublished operation, execute [Observed cancellation](cancellation.md) after complete bound issue/release discovery and **before capture**. Resume its saved apply/disclosure records first. If it observes a request or hand closure for the intended order, finish/report cancellation and stop this send, preserving every pending record, snapshot, ZIP, draft, checklist, tag reservation and design folder. Run the same owner immediately before publication with fresh complete observations. An earlier successful check never authorizes a later unchecked publication. A packaged matching published final follows Send recovery first and is never cancelled by a later request.

1. Reconcile `.designeritl/pending/` and `state.pendingDeliveryIndex` before a new send. A valid existing capture/ZIP is authoritative; do not recapture source edits. Multiple pending deliveries require an explicit choice. Preserve unsupported or conflicting evidence and stop.
2. Use Sending's `selectOrder` with complete current issue/release observations. Reconcile its pending results before fresh selection. Reuse the active available open order or obtain an explicit open-order choice before asking about versions. An unstarted choice uses Orders' canonical activation/checklist policy. Preserve repository/order and activation UUID for compare-and-clear. Apply observed cancellation before capture. A closed order without matching published final is cancelled; a published final blocks a new delivery. Cancellation requests are not startable orders.
3. Call Sending's `selectVersion`, recommending the most recently edited but obtaining an explicit numbered choice. Delivery selection does not move `.current`; preserve the selected source folder and number. Call Sending's `reserve` with complete tags/releases (including drafts), the chosen order/version and send kind. It allocates one random delivery UUID/fixed capture time, reserves the next nonfinal send tag above all remote/local evidence or the fixed final tag, and saves the pending identity/index/ledger before remote mutation. Occupied identities conflict; never renumber a retry.
4. Use that saved schemaVersion 1 record under `.designeritl/pending/UUID/record.json`. Create its snapshot parent, then call Format's `capturePrototype(sourcePath, stagingPath)` for `snapshot/<capturedFolder>/`. It compares complete source-before, copied and source-after inventories and directory lists, retaining empty directories. Save `capturedInventory`, `payloadSha256` and `capturedDirectories` only after it returns successfully, through Project's validated owner-record replacement. Any mismatch or interrupted copy prevents completing capture. Reconcile partial staging through Send recovery, retaining the failed attempt. After coherent capture, all checks and retry operate on these saved bytes.

## Assess the captured design

5. Establish [Versions portability](versions.md) against the capture. Open its entry HTML directly, exercise relevant states/interactions, and observe network attempts. Save evidence with the payload hash and performed/omitted checks. Unresolved dependencies, missing required checks or format violations block either send and cannot be acknowledged away.
6. For final delivery only, use Orders' `createOrders(format).readChecklist(projectRoot, orderNumber)` to validate the saved agreement and checkpoint, and retain its scope, local checkedOrdinals and taskContext as separate snapshots. `scopeSha256` is `scope.originalBodySha256`, never a hash of tick-edited Markdown or the current remote issue. Assess **every** `scope.tasks` definition in its original order against the captured selected version as fulfilled, unfinished or unknown, with actual evidence or a reason for uncertainty. An older delivery selection may contradict current local ticks; assess its snapshot, not `.current`. Unknown counts as unfinished. Freeze `evidence/reassessment.json` as exact UTF-8 JSON containing payloadSha256, scopeSha256, `agreedScope: scope` and ordered `{ordinal,result,evidenceOrReason}` tasks. The embedded original body proves the complete agreed task universe to reception. Delivered unchecked ordinals are every task not both locally checked and reassessed fulfilled. Preserve local progress; sending or acknowledging does not tick tasks.
7. For final delivery only, disclose the exact unchecked task numbers/text and reassessment reasons. Obtain the designer's applicable completion choice. An explicit final-delivery invocation authorizes a fully fulfilled, locally checked scope; a sufficiently specific conditional authorization may cover its stated conditions. Unfinished, unknown or locally unchecked tasks require the designer's explicit acknowledgment of every derived ordinal. Decline or missing authorization retains evidence and leaves the order open before packaging. Freeze `evidence/decision.json` as exact UTF-8 JSON with `schemaVersion:2`, payloadSha256, scopeSha256, reassessmentSha256, acknowledgedUnfinishedOrdinals, the genuine explicitDesignerStatement and UTC recordedAt. Hash stored exact bytes. Any changed payload, agreement, reassessment bytes or applicable task progress invalidates the earlier decision. Preserve stale evidence and obtain a new applicable choice. A user who wants a different version can explicitly replace the un-packaged capture through Send recovery, then repeat portability, reassessment and completion.

## Freeze and publish

8. Write one exact `manifest.json` in pending storage using the fields defined by Format; a new nonfinal send uses Sending's `nonfinalManifest` with `evidence: null` and `deliveredUncheckedOrdinals: null`. Copy the captured file inventory and complete `directories` list into it so empty prototype directories remain part of its declared structure. Include agent-written deliveryNote summary naming this order/version, outsideOrder and workInProgress (explicit `None` when applicable). Retain scope hash and local progress separately from any final reassessment. Only final manifests embed frozen reassessment/decision evidence. Call `packageDelivery` on stored manifest bytes and snapshot; persist `delivery.zip`, `descriptor.json` and human release notes containing its single `designeritl-delivery` block. Read back and call `verifyDelivery` before proceeding. Persist payload/ZIP/manifest hashes and asset size in record, then call `verifyPendingDelivery(pendingRoot, repositoryId)` before remote mutation. Never regenerate a completed package on retry.
9. Follow [Send recovery's draft creation guard](send-recovery.md#guard-draft-creation) with complete release pages and tags. A zero-match listing alone never permits creation. Format's `beginDraftCreation` must durably save and reread a descriptor-bound attempt before `gh release create TAG --repo OWNER/NAME --draft --title TITLE --notes-file NOTES` (or the equivalent draft-only REST POST). After a successful or uncertain response, reconcile the same identity. An unresolved attempt or legacy record without attempt evidence permits only read-only reconciliation until the owned release appears; independently proven non-dispatch follows the retained-proof branch. Draft creation is not publication.
10. For a matching owned draft, list all assets. If delivery.zip is absent, `gh release upload TAG ZIP --repo OWNER/NAME`. If it exists, download to separate verification staging (`gh release download TAG --repo OWNER/NAME --pattern delivery.zip --dir ABSENT_OR_EMPTY_DIRECTORY`) and verify exact bytes with the descriptor. Reuse exact owned assets. Preserve evidence of a bad owned unpublished asset and require a deliberate repair before deleting only that asset. Never blind `--clobber`, alter a foreign asset or mutate a published release.
11. Reverify saved capture, manifest, evidence bindings and ZIP. Re-read complete cancellation/issue state immediately before publication; observed cancellation refuses publication and leaves the draft/evidence intact. If open and uncancelled, `gh release edit TAG --repo OWNER/NAME --draft=false`. A lost response is reconciled by reading the release, never by recreating it.
12. Fetch actual release metadata (tag, draft=false, ID, single descriptor and asset identity). Download its actual asset to fresh verification staging and `verifyDelivery` again. Compare all saved identity fields and exact ZIP/manifest hashes. Unknown remote state or a mismatch prevents closure or a success claim.

## Complete

13. A nonfinal verified publication leaves the issue open, retains assignment and working marker, and records completion. A final verified publication closes the order: `gh issue close N --repo OWNER/NAME --reason completed`; then independently read back closed status. If publication succeeded and closure failed, retry closure/bookkeeping only, reusing frozen evidence and exact ZIP. An already closed issue following matching published final completes bookkeeping. Developer acceptance is separate and never recorded as implied approval.
14. Re-read current state and clear assignment only for final completion, and only if repository/order AND activation UUID equal `record.assignmentToken`. Preserve a later activation, even of this same order. Preserve checklists and working marker. Through Project's complete-record replacement, add or reconcile one `completedDeliveries` entry containing delivery/repository/order identity, tag/kind, release/asset IDs, exact hashes, evidence path and verification/completion time; remove only this UUID from `pendingDeliveryIndex`. Re-read state and verify these effects before marking the pending record locally complete. An existing completion entry must match the same identity/hashes; conflicting entries stop bookkeeping. Retain capture/ZIP and observations after success; cleanup is a later explicit action. Report exact tag/UUID, verification and any remaining closure failure.

Incoming requests created after the final pre-publication check do not withdraw a published delivery. Inbox later names such deliveries while applying cancellation; a request after published final has no effect. This follows observed cancellation, not an impossible atomic GitHub issue/release transaction.
